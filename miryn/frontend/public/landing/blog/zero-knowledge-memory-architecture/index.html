Under the Hood: 384-Dim pgvector, Zero-Knowledge Fernet Encryption & Sub-1.5s Recall

Sep 18, 2026 • 9 min read • By Sahil Sharma

Designing an AI companion that genuinely evolves with a human requires solving two fundamentally opposed engineering challenges: sub-second conversational latency and deep, privacy-preserving semantic memory. Here is an architectural deep dive into how Miryn solves both.

Most AI memory systems fail because they treat context as a simple database lookup or an overwhelming prompt dump. Shoving tens of thousands of tokens into an LLM context window is not only slow and expensive — it degrades needle-in-a-haystack attention and leaks private data.

Miryn implements a hybrid three-tier memory architecture coupled with asynchronous identity extraction, powered by FastAPI, PostgreSQL with pgvector, Redis, and Celery.

1. The Three-Tier Memory Hierarchy

Memory is not monolithic. Human cognition separates fleeting sensory input, short-term situational memories, and permanent core beliefs. Miryn models this directly:

Memory Tier Storage Engine Lifecycle / TTL Purpose & SLA
Transient Memory Redis Cluster 2 Hours TTL Active chat thread, rate-limit counters, idempotency cache (<10ms)
Episodic Memory PostgreSQL + pgvector 7-Day Auto-Expiry (delete_at) Recent contextual events, task states, situational references (<80ms)
Core Identity Memory PostgreSQL (identities) Immutable / Versioned Traits, values, beliefs, patterns, open loops (Unique user_id + version)

2. 384-Dimensional Embeddings & Hybrid Scoring Algorithm

Episodic memories are embedded using a compact, high-precision 384-dimensional dense vector space. While 1536-dim embeddings are popular, 384-dim representations offer 4x faster cosine distance calculations, significantly lower memory pressure, and zero quantization loss on conversational semantics.

Context retrieval does not rely solely on raw vector similarity. A memory from five minutes ago has different relevance than a memory from five days ago, regardless of semantic distance. We use a composite scoring function:

Score(M) = α · CosineSim(q, v_M) + β · e^(-λ · Δt) + γ · Importance(M) Where: • CosineSim(q, v_M): Dense vector dot product in 384-dim space • e^(-λ · Δt): Exponential temporal decay over elapsed hours • Importance(M): Weight assigned by reflection worker (1.0 to 5.0) • α = 0.55, β = 0.25, γ = 0.20 (empirically tuned for conversational coherence)

The entire retrieval pipeline is bounded by a strict 1.5-second timeout budget. If pgvector vector search or Redis queries lag, the orchestrator gracefully degrades to transient context, ensuring the user is never left waiting.

3. Zero-Knowledge Cryptography: Fernet Payload Encryption

Every message payload and personal trait stored in Miryn is encrypted using Fernet symmetric cryptography before writing to the database table:

  • Cipher: AES-128 in Cipher Block Chaining (CBC) mode with PKCS7 padding.
  • Authentication: HMAC-SHA256 authenticated envelope preventing ciphertext manipulation.
  • Key Isolation: Cryptographic keys are injected via environment variables and never logged or exposed to the client.
Dual-Path Database Execution:
Every database operation in Miryn implements both SQLAlchemy parameterized SQL via text() with named binds for native Neon PostgreSQL / pgvector, alongside a fallback adapter for Supabase REST clients. Parameterization guarantees total immunity against SQL injection vulnerabilities.

4. The Asynchronous Reflection Pipeline

Generating deep insights — such as identifying recurring behavioral traps or tracking open loops — takes substantial compute. Blocking the user's chat message while an LLM conducts deep introspection would destroy the real-time conversational experience.

Miryn offloads all identity synthesis to a Celery background queue. Once the message response is returned to the user, a fire-and-forget task triggers reflection.analyze. The worker extracts new beliefs, flags open loops, increments pattern counters, and logs the change to identity_evolution_log. The updated state is then pushed live via Server-Sent Events (SSE) to the frontend.
